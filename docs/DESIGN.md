# 仓门扫描对账台设计
预约单以箱号为主键，声明订单、托盘、数量、月台、窗口、净重及容差。输入扫描流为 JSONL，每条有稳定事件身份、UTC 时间、箱号、动作和来源字段。文件哈希冻结来源；事件身份重复且内容不同进入冲突记录。

数据流：预约配置 → 来源文件 → 事件规范化（时间、设备、设备内 seq 分列存证）→ **证据化因果重建** → 装卸状态机与拆并箱谱系 → 数量、称重、月台核对 → 差异结算 → JSON/Markdown 交接报告。

## 事件因果重建

月台扫描来自不同设备时会出现相同时间戳。数据库自增 id 只记录导入先后，**不能**证明同刻跨设备事件的先后；文件顺序同样不具证明力。因此系统不再按 `time,id` 静默排序，而是构建有向因果图，边只允许来自四类有证据的约束：

- `time_order`：严格更早的 UTC 时间戳（同刻不加边）；
- `device_seq`：同一设备内单调递增的 seq，与时间戳矛盾时两边成环并保留 `device_order_conflict` 证据；
- `stage_order`：同一货箱 `gate → unload → check → exit` 的阶段约束；
- `lineage_split` / `lineage_merge`：拆箱事件先于子箱全部事件，并箱父箱全部事件先于并箱事件。

图的每条边连同依据写入 `causal_edge` 表。同刻且互相不可达的事件对记录为“顺序不可证明”的原始证据（含 event id、设备、seq、动作），报告中逐条列出，绝不把猜测顺序伪装成时间事实。

合法事件顺序即因果图上满足阶段状态机的拓扑序，由 DFS 枚举（上限 2000，超限给出 `order_enumeration_limit`）。事件级因果环意味着无合法拓扑顺序（`no_legal_order`）；拆箱血缘图上回到祖先的路径为 `lineage_cycle`（拆后并回同箱是合法重聚，不计入血缘环）。设备 seq 缺口记录为 `seq_gap`，只挂在使用该设备的货箱上。

## 两种结论政策（操作方显式选择）

- **严格模式 `strict`**：要求时间顺序可证明。只要货箱证据闭包内的合法事件顺序不唯一，即标 `pending` 并附 `order_not_provable` 与同刻事件 id。
- **共识模式 `consensus`**：枚举全部合法顺序并逐一模拟收货结论；只有每种顺序都得到相同结论（状态、收货量、重量、问题集合）才允许该结论落地，否则 `pending` 并附 `conclusion_diverges` 与全部候选结论。

拆箱事件的声明数量不得超过该顺序下此前已卸量，违反记 `split_exceeds_unloaded`——这是顺序相关的数量约束，可使不同合法顺序对同一货箱产生不同数量结论。称重采用同顺序内最后生效值，因此同刻冲突称重会产生不同重量候选。

合法装卸顺序是 `gate → unload → check → exit`。称重与拆并箱事件不推进此状态。错误码 `illegal_transition` 阻断交接；缺少阶段为 `missing_stage`。拆箱 `children` 与并箱 `parents` 的数量之和须等于事件声明数量，只有守恒的关系写入 `lineage`。数量差异区分 `shortage` 与 `overage`，缺重为 `missing_weight`，越容差为 `weight_mismatch`。月台或时间窗口不符是 `wrong_dock_or_window`。未知箱号保留 `unknown_box` 问题。

决策为 `accepted`、`pending` 或 `blocked`。阻断问题不会因其他正常扫描被覆盖；缺少证据不会得到 accepted；因果不确定性（含 seq 缺口）同样禁止 accepted。问题与证据按货箱证据闭包隔离：谱系环、无合法顺序、序号缺口只影响相关收货单，不污染无关单据。每次重算只更新决策、业务问题、谱系与因果边，来源和原始事件不可变。配置文件哈希冻结在数据库；修改预约单须使用新工作区。当前只处理单批次本地扫描，不与仓储系统或承运人联网。
