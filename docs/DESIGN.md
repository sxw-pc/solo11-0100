# 仓门扫描对账台设计

预约单以箱号为主键，声明订单、托盘、数量、月台、窗口、净重及容差。输入扫描流为 JSONL，每条有稳定事件身份、UTC 时间、箱号、动作和来源字段。文件哈希冻结来源；事件身份重复且内容不同进入冲突记录。

数据流：预约配置 → 来源文件 → 事件规范化 → 事件时间排序 → 装卸状态机与拆并箱谱系 → 数量、称重、月台核对 → 差异结算 → JSON/Markdown 交接报告。

合法装卸顺序是 `gate → unload → check → exit`。称重与拆并箱事件不推进此状态。错误码 `illegal_transition` 阻断交接；缺少阶段为 `missing_stage`。拆箱 `children` 与并箱 `parents` 的数量之和须等于事件声明数量，只有守恒的关系写入 `lineage`。数量差异区分 `shortage` 与 `overage`，缺重为 `missing_weight`，越容差为 `weight_mismatch`。月台或时间窗口不符是 `wrong_dock_or_window`。未知箱号保留 `unknown_box` 问题。

决策为 `accepted`、`pending` 或 `blocked`。阻断问题不会因其他正常扫描被覆盖；缺少证据不会得到 accepted。每次重算只更新决策、业务问题与谱系，来源和原始事件不可变。配置文件哈希冻结在数据库；修改预约单须使用新工作区。当前只处理单批次本地扫描，不与仓储系统或承运人联网。

## 仓门暂存区有限班次温控

冻结的 `climate_case` 携带 D1/D2 真实仓门扫描事件、本地传感器 CSV 原始字节与 SHA、逐时段外界增温、各仓门温度上限、共享冷却机能力、分时电价（整数分）与两份授权运营目标。温度动力学按仓门逐时段递推：`终点温度 = 起点温度 + 环境增温 − 实际分配冷却量`，起点取上一时段真实读数（若已反馈）或预测温度。仓门暴露为 `max(0, 终点温度 − 上限)`，各时段正温差求和，缺测从不按零处理；总暴露受合同上限约束。共享冷却机每时段最多服务一个仓门，命令给出确切仓门与时隙，同一时段不可能同时冷却 D1/D2。

优化器（`climate_opt.solve`）用动态规划枚举全部可行命令序列：每个标签携带量化后的各仓门温度、逐仓门累计暴露、整数电费与动作路径；仅当两条路径到达完全相同的温度状态时才合并并保留字典序更优者，不同状态全部保留——因为更热的仓门在后续时段仍可被冷却，跨温度分量的支配剪枝会丢失最优解。两份目标共享同一动力学与总暴露上限，仅排序键不同：`min_energy` 依次按（电费，最大仓门暴露，总暴露）排序，`min_max_dock_exposure` 依次按（最大仓门暴露，总暴露，电费）排序；最终的动作路径分量保证相同输入重算稳定。证据字段记录评估节点数、剪枝标签数、分支因子与最优排序键，可独立暴力复核。

校验失败（传感器身份冲突、时区不一致、增温缺项、冷却量非物理、容量不足、双仓门同时请求等）整份建议进入 `climate_hold`，不发布任何部分命令。无可行计划同样只登记待核。迟到的真实传感器读数按周期边界写入 `climate_reading`：已执行时段的设备命令与历史计划版本不可变，新读数只校正剩余时段起点并求解后缀，生成新版本；偏差逐仓门记录预测与真实终点温差。若已发生暴露本身超过合同上限，版本标记 `breached` 并明确报告不可追回量，未来时段不会产生负暴露抵消。

`climate_command` 保存可执行设备命令（时段、仓门、实际电费、executed/pending 状态），`climate_trajectory` 保存每时段每仓门起点/增温/冷却量/终点/上限/暴露/价格/来源/机台占用，`climate_plan` 保存目标、版本、状态、来源摘要与最优性证据，`climate_hold` 保存待核原因。报告在原有收货决策之外追加 JSON 与 Markdown 的温控段落；收货 `accepted/pending/blocked` 不被温控流程改写。
